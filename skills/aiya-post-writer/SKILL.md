# 资源帖起草 v0.8

## 这个技能做什么

把一部作品的事实整理成一行可直接推送的草稿。产出固定三样：`title`、`content`（HTML 片段）、`terms`（六个词法）。状态、作者、发布时间、文件列表由发帖器按设置决定，技能不产出这些。

自动化负责**可核对的部分**：核实作品信息、搬官方字段与官方图、把事实整理成读者认得的结构、把来源记清楚。字段查得比手写时代更全是正常的——格式是承载，不是目的。判断留给站长——推荐语怎么写、哪版差异值得提、这部作品要不要发，都是人的事。

机械步骤（网盘上传、杀毒测试、解压校验、启动程序截图）以后各自固化成脚本；跑哪些、按什么顺序，由我现场判断。这些步骤不在本技能里，见文末「扩展位」。

**内容类型自己判。** 判的不是「八个模板选一个」，而是两个独立的轴：**载体**（这是什么东西）决定字段与标题，**形态**（一个还是多个、首发还是分流）决定正文怎么组织。判完写一行声明再落笔，见 `references/dispatch.md`。

## 第 0 步：探活

```bash
node skills/aiya-post-writer/scripts/publisher.mjs health
```

命令在**发帖器仓库根目录**执行。不在仓库里时，把 `skills/aiya-post-writer/scripts/publisher.mjs` 换成技能目录的绝对路径——脚本不依赖仓库任何文件，只有这个相对路径依赖工作目录。

返回 `{ base, app, version, port, pid, startedAt, uptimeSec, dataDir, configured, defaultStatus, ingestMaxRows }`。

| 结果 | 含义 | 动作 |
|---|---|---|
| 退出码 1，「连不上发帖器」 | 服务没起 | 请用户启动桌面版或 `npm run dev` |
| `app` 不等于 `aiya-publisher` | 那个端口上是别的东西 | 报给用户，不猜、不重试 |
| `configured: false` | 站点/账号/应用密码没配齐 | 起草照常；在回报里说明「推送时图片传不进图床」 |
| 正常 | —— | 记下 `version` 与 `dataDir`，继续 |

`version` 与本文档的形状对不上时，先怀疑版本，再怀疑自己的理解。

## 端点表

六个具名命令，五条操作、一条前置。地址由脚本解析（`PUBLISHER_BASE` 优先，否则探默认端口并用 `/api/health` 的 `app` 字段确认身份），文档与 payload 里都不出现接口 URL。

| 命令 | 底层端点 | 作用 | 写库 |
|---|---|---|---|
| `health` | `GET /api/health` | 探活、身份、配置状态 | 否 |
| `context` | `GET /api/ingest/context` | 六词法（id/路径/次数）、作者、默认值、行数上限 | 否 |
| `lookup` | `GET /api/state` | 本地查重（脚本只投影标题相关字段） | 否 |
| `stage` | `POST /api/images` | 图片复制进 `<dataDir>/images`，回 `file://` 引用 | 只写图片文件 |
| `preview` | `POST /api/ingest/preview` | 校验 + 归一化，不入库 | 否 |
| `ingest` | `POST /api/ingest` | 入队为待推送的脏行 | 是 |

参数、返回结构、报错对照见 `references/api.md`。

## 硬约束

1. **六个命令是全部权限**。站点 REST、数据库文件、推送、删行、改设置都在技能之外。草稿入队后停在「待推送」，推送是人的动作。
2. **只新建行**。`lookup` 命中同名或高度相似的行，把结果交给用户定夺（跳过 / 换标题 / 他先处理）。
3. **类型先声明再落笔**：一行 `按 <载体> · <形态> 处理（依据：…）`。判错载体的代价是整篇结构错——图集写成字段清单、合集写成单部规格——声明外显了，人才截得住。只在两轴信号互相打架时停下问人（`references/dispatch.md` 末节）。
4. **格式素材在 references，按需取，本文不重复**。`writing.md` 是工具箱（八个格式零件各装什么、什么时候会反效果），不是模板；标题 `titles.md`、短代码 `shortcodes.md`、配图 `images.md`、判型 `dispatch.md`、接口 `api.md`。
5. **正文是 WordPress 正文**：段落由空行切（`wpautop`），源里不写 `<p>`，只有需要结构时才上标签。这是平台行为，不是风格偏好，细节在 `writing.md` 前两节。
6. **不确定的字段留空**。版本号、发售日、社团、CV、语言、平台没查到就整行删掉。查不到的事实不进正文。

## 输入判断

| 输入 | 判断 | 做法 |
|---|---|---|
| **A. 只有作品名** | 一个词、一个标题，没有正文 | 先定身（同名作品很多：平台、社团、年份至少确认一个），再走完整流程 |
| **B. 一段作品介绍** | 用户贴的简介 / 官网文案 / 商店描述 | 先抽原文里已有的事实，再检索补齐；照抄部分进 `<blockquote>`，出处记进 `[internal]` |
| **C. 一个目录** | 给了本地路径 | 先 `ls` 看清结构：一堆作品文件夹 → 每个走 A/B；单部作品的多文件 → 当作一部，从 readme/txt 提事实 |
| **D. 一批作品** | 列表、合集、多行文本 | 拆成单行逐个处理，但先拿 1 行跑通 preview → ingest，用户认可标题与词法风格后再批量 |

输入含糊到无法定身时，问一次（原名 / 社团 / 平台任一个线索）。

## 工作流

1. `health` —— 前置，见上。
2. `context --lines` —— 拿词法与默认值。分类**用 id**（接口按名称精确匹配，同名会折叠）；其余词法优先 id。
3. `lookup "<作品名片段>"` —— 查重。命中就交给人。
4. **核实**（联网检索）—— 按 `references/verify.md` 走：来源分 T1 官方 / T2 权威二手 / T3 用户内容，字段先找 T1；每个字段心里有证据等级，只把 A（官方确认）与 B（多源一致）写进正文；来源打架按「是否不同版本 → 谁更新 → 如实并列」处理，不挑顺手的那个。核实时同时记下**能判类型的信号**（来源域、编号形态、有没有卷数/张数/文件结构）和**风险信号**（包内可执行文件、需要写系统目录、二次打包），后者决定要不要挂 `[alert]`。这一轮只求定身；判完类型再回到 `types/<载体>.md` 的「采信数据源」表逐行精查字段。
5. **判类型并声明** —— 读 `references/dispatch.md`，定载体与形态，写一行声明，接着走。
6. **配图** —— 按 `references/images.md` 找封面，`stage` 拿 `src`。
7. **写 payload** —— 标题按 `titles.md`，正文与词法按 `writing.md`，命中的 `references/types/<载体>.md` 给该类型的字段、搜索词与采信边界、常用组合与分类候选，短代码按 `shortcodes.md`。**只读命中的那一份 type**。表里的搜索词照抄着用，不自己另想搜索点；表里没有的站点，字段宁可不写。
8. **落笔后自查一遍** —— `writing.md`「别写成 AI 腔」的十条，逐条扫正文；`writing.md` 末尾的自检清单逐项打勾。自查不是重写，只删多余与替换成事实。
9. `preview payload.json` —— `errors` 清零；`warnings` 逐条读（同名术语折叠、未知词法都在这里露出）。
10. `ingest payload.json --source "agent/<批次名>"` —— 记下 `localIds`。
11. **回报** —— 判定行 + 标题清单 + `localIds` + 没查到的字段 + 来源冲突 + 风险信号 + 新造的词（`name:` 会在推送时由站点创建）+ 建议人工核对的地方。归入 `other` 的额外说明「分类未定」。

## 要收集的字段

各类型的字段清单在 `references/types/*.md`（字段型的几种有惯用字段名，来源里还有别的硬信息可以照格式加）。共用检索锚点：**原文名**（必填，标题与检索都靠它）、中文译名或通称、类型、原作/系列、社团/作者、角色、发售日/版本/语言/平台、官方简介、内容要点（玩法、曲目数、页数、时长）。查不到的留空，不写「未知」。

## 落笔前读什么

- `references/dispatch.md`：**每次必读**。载体与形态的信号表、冲突规则、哪些机械步骤值得跑。
- `references/titles.md`：**每次必读**。标题语法、七个载体的填法、正例与负例。
- `references/verify.md`：**每次必读**。来源分层（T1/T2/T3）、搜索阶梯（编号优先 / 原文名 + 站点名 / 落页三判据）、证据等级（A/B/C/D）、冲突处理、查到哪算够、风险信号。
- `references/writing.md`：**每次必读**。WP 渲染口径、格式工具箱（九个工具各装什么、什么时候用会反效果）、几种组合示例、字段块两种形式、AI 腔自查、红线、六词法。存量数字只说明常见程度，不是配额。
- `references/shortcodes.md`：短代码的目录表与属性——磁力进 `[clip_board]`、危险操作进 `[alert]`、来源进 `[internal]`、长清单进 `[collapse]`。落笔前扫一眼目录表。
- `references/types/<载体>.md`：**只读命中的那一个**。识别信号、采信数据源（站点 / 搜索词 / 采信边界）、字段清单、该载体常用组合、分类候选。
- `references/images.md`：封面从哪找、什么算合格、为什么必须第一张。
- `references/api.md`：六个命令的参数与返回、payload 字段、常见报错。

## 扩展位（后续子技能）

本技能是入口。将来按输入分支挂子技能，契约固定：子技能只产出**事实**或**已 `stage` 的图片**，不碰发帖器状态、不改行；跑哪些由我判断，怎么跑由脚本固化。

| 触发条件 | 子技能职责 | 产出 |
|---|---|---|
| 输入是压缩包（.zip/.rar/.7z） | 解包读 readme / 目录结构 / 内附截图 | 文本事实 + 内附图片 |
| 输入是可运行程序，且用户在场 | 启动程序取真实截图（标题画面、界面） | 截图文件（再由本技能 `stage`） |
| 输入是整站或整页链接 | 抓页面结构与图集 | 文本事实 + 候选封面 |
| 需要挂网盘 / 杀毒验证 | 跑固化脚本，回报链接与结论 | 文件列表字段 + 验证结论 |

新增分支在这里登记触发条件与产出契约，主流程的六个命令与产出字段保持不变。哪条作品值得跑哪个步骤看载体——`references/dispatch.md` 末节有「载体 → 值得跑的步骤」对照；拿不到的数字就留空。
