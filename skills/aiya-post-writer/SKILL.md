# 资源帖起草

把一部作品的零散信息变成发帖器里可以直接推送的草稿行：核实、配图、写正文、选词法、入队。人工在发帖器里过一遍再推。

产出只有三样：`title`、`content`（HTML 片段）、`terms`（六个词法）。**状态、作者、发布时间、网盘文件列表由发帖器按自己的设置决定，不要输出这些字段**——输出会被忽略或误伤既有设置。

## 边界（硬约束，优先于任何效率考虑）

1. **只能调本技能的五个命令**（`context` / `lookup` / `stage` / `preview` / `ingest`）。不直接请求站点 REST，不改数据库文件，不推送，不删行，不动设置。推送是人的动作：草稿入队后停在「待推送」。
2. **只新建行，不修改已有行**。`lookup` 命中同名或高度相似的行时，停下来把命中结果交给用户，由用户决定是跳过还是另起标题。
3. **正文里不能出现远程图片地址**（`https://…` 直链、外链图床、社交平台图片 CDN）。图片必须先 `stage` 落到发帖器本地，正文引用它回的 `src`。推送时发帖器才把它传进站点图床——站点封面只认站点自己托管的图，外链图会让封面静默失效。
4. **不确定的信息不写**。版本号、发售日、社团名、CV、语言没查到就留空或不写，不要按印象补全，不要写「据推测」。
5. **不写站内机制**：不提「回复可见」「积分下载」「解压密码」，不写网盘链接与提取码（那是发帖器文件列表的活）。不写 `<script>`、`<style>`、内联 `style=`、`on*=` 属性。

## 开工前

发帖器要在跑：桌面版开着，或在仓库里 `npm run dev`。命令一律在仓库根目录执行：

```bash
node skills/aiya-post-writer/scripts/publisher.mjs <命令>
```

端点地址由脚本自己解析（`PUBLISHER_BASE` 优先，否则探默认端口）。**不要在正文、payload 或回答里拼接口 URL**——端口是可变的，唯一稳定的东西是上面这五个命令名。

连不上时脚本会说「连不上发帖器」，这时让用户先启动，而不是换别的方式写库。

## 五个命令

| 命令 | 干什么 | 什么时候用 |
|---|---|---|
| `context` | 六词法（id/路径/使用次数）、作者、默认状态、单次行数上限 | 每次开工第一件事；`--lines` 打成文本更省上下文 |
| `lookup <文本>` | 本地查重：标题含该文本的行 | 定标题前后各一次 |
| `stage <文件>` / `stage --url <地址>` | 图片复制进本地 images 目录，回 `{path, src, name}` | 拿到封面/截图后 |
| `preview <payload>` | 校验 + 归一化，**不写库** | 写完 payload 必跑 |
| `ingest <payload>` | 入队为待推送的脏行 | preview 干净后 |

参数细节、返回结构、payload 完整示例见 `references/api.md`。

## 先判断输入属于哪一类

| 输入 | 判断 | 做法 |
|---|---|---|
| **A. 只有作品名** | 一个词、一个标题，没有正文 | 全靠检索：先确认是哪一部（同名作品很多），再走完整流程 |
| **B. 一段作品介绍** | 用户贴来的简介/官网文案/商店描述 | 先读原文抽出既有事实，再用检索补齐缺的字段；**原文照抄部分用 `<blockquote>` 引起来并注明来源**，不要改写成自己的话混进正文 |
| **C. 一个目录** | 给了本地路径 | 先 `ls` 看清结构：一堆作品文件夹 → 每个作品走 A/B；单个作品的多文件 → 当作一部作品，从里面的 readme/txt 提事实 |
| **D. 一批作品** | 列表、合集、多行文本 | 拆成单行逐个处理，但**先拿 1 行跑通 preview → ingest**，确认词法和标题结构合用户口味，再批量跑剩下的 |

输入含糊到无法判断是哪部作品时，问一次（原名/社团/平台任一个能定身的线索），不要靠猜写一篇假帖。

## 工作流

1. **取参照**：`context --lines`。记住单次行数上限、默认状态、作者名单；词法按使用次数排序，次数高的更可能是站内既有用词。
2. **查重**：`lookup "<作品名片段>"`。有命中就把结果交给用户；没有才继续。
3. **核实**（联网检索）：按下面的字段表收集事实，以官方源为准——官网 / 商店页（Steam、DLsite、FANZA、BOOTH）/ 社团或作者主页 / 官方 SNS。二手源（wiki、评测、论坛）只用来补齐官方页没写的字段，并在正文里标成「来源」。
4. **配图**：按 `references/images.md` 找封面，下载后 `stage`，拿到 `src`。
5. **写 payload**：按 `references/writing.md` 写标题、正文、六个词法。
6. **校验**：`preview payload.json`。`errors` 必须清零；`warnings` 逐条读（同名术语折叠、未知词法都出现在这里）。
7. **入队**：`ingest payload.json --source "agent/<批次名>"`。记下返回的 `localIds`。
8. **回报**：标题清单 + `localIds` + 哪些字段没查到、哪些词是新造的（`name:` 会在推送时由站点创建）、建议人工核对的地方。

## 要收集的字段

| 字段 | 用途 | 查不到时 |
|---|---|---|
| 日文/原文名 | 标题里的原文名、检索关键词 | 必填，查不到就问 |
| 中文译名 / 通称 | 标题主名 | 可省，用原文名 |
| 类型（游戏/音声/漫画/动画/画集…） | 标题前缀、`resource_category` | 必填 |
| 原作 / 系列 | `resource_original` | 原创作品填「原创」类既有词，或留空 |
| 社团 / 作者 | `resource_author` | 留空，不猜 |
| 角色 | `resource_character` | 只有明确列出的角色才写 |
| 发售日 / 版本 / 语言 / 平台 | 正文说明段、标题版本标记 | 留空 |
| 官方简介 | 正文 `<blockquote>` | 用商店页描述，注明来源 |
| 内容要点（玩法、曲目数、页数、时长…） | 正文条目 | 只写查到的，不推测 |

## 写正文之前先读

- `references/writing.md`：标题结构、正文骨架、允许的标签、六个词法的取舍规则（**分类必须用 id**，这是最容易写错的一处）。
- `references/images.md`：封面从哪找、什么算合格、`stage` 之后怎么放进正文、为什么必须放第一张。
- `references/api.md`：五个命令的参数与返回、payload 字段语义、常见报错。

## 扩展位（后续子技能）

本技能是入口，不是全部。将来按输入分支挂子技能，契约固定为：子技能只产出**事实**或**已 `stage` 的图片**，不碰发帖器状态，不改行。已知规划中的分支：

| 触发条件 | 子技能职责 | 产出 |
|---|---|---|
| 输入是压缩包（.zip/.rar/.7z） | 解开读 readme / 目录结构 / 内附截图，提取原名、版本、社团 | 文本事实 + 内附图片 |
| 输入是可运行程序，且用户在场 | 启动程序取真实截图（标题画面、界面） | 截图文件（再由本技能 `stage`） |
| 输入是整站或整页链接 | 抓取页面结构与图集 | 文本事实 + 候选封面 |

新增分支时在这里登记触发条件与产出契约，不要把它们写进主流程——主流程的五个命令和产出字段保持不变。
