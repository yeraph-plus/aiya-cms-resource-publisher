## 哪些是硬的，哪些是软的

先分清两件事，后面所有规则都建立在这条线上：

**硬的（平台行为与内容责任，不可改）**

- WP 的渲染机制：段落由空行切，不手写 `<p>`，封面取正文第一张图，短代码按空行独立成块。
- 可核对：每个数字、每个字段都能指回来源；不写评分、推荐、玩梗。
- 权限：六个命令，草稿停在待推送。

**软的（站内既有的写法，可改）**

站内 558 篇 resource 帖是过去手写的，里面有大量个人习惯：固定的三个小节名、几乎都只放一张图、标题一律两前缀。这些是**读者已经认得的形状，照写能省读者的适应成本**，但不是必须。这一版由 agent 跑中立信息，字段可以比手写更全、结构可以按内容重新组织：

- 小节怎么分、要不要分节，看内容有几块，不是看存量帖怎么分。
- 图放几张，看图本身有没有信息量。
- 篇幅写到事实说完为止。
- 标题的名额按需要花。

存量数据在这份文档里只以「篇数」的形式出现，作用是说**常见程度**，不是配额。看见「195 篇写 `目录：`」，意思是「这么写读者不会觉得陌生」，不是「只准这么写」。

## WordPress 怎么渲染正文

正文存进 `post_content`，**段落不是你写的，是渲染时按空行切的**（`wpautop`，过滤器优先级 10）。由此三条硬规则：

- **段落之间空一行**。单换行只产生 `<br />`，两句话会挤进同一段。块级元素（图、列表、引用块、分隔线、标题、短代码）之间也各留一行空行。
- **不写 `<p>` / `</p>`**。写了不会坏，但多余，而且和自动分段在短代码、列表边界叠在一起时会留空段落。
- 纯文本能说清的就写纯文本，需要结构时才上标签。

短代码也是按这条走的：**独占一行、前后各空一行**，紧贴文字会被塞进段落里。

## 工具箱

八个工具，按「它替读者省了什么」来挑，不按版式挑。

| 工具 | 装什么 | 替读者省了什么 | 反效果 |
|---|---|---|---|
| 纯文本段落 | 说明、版本差异、运行注意事项、剧情概述 | —— | 该分块的地方也写成一段，长到没人读 |
| `<hr />` | 分区：封面与简介区 / 正文区之间 | 视觉上把「这是什么」和「怎么用」切开 | 一帖超过两条，页面碎成条 |
| `<h3>` `<h4>` | 给一段内容取名字（字段组、简介、归档说明、安装、目录） | 长正文里有路标，能跳读 | 内容撑不起来的分节比不分节更难看；没有并列关系的小节不要立 |
| `<blockquote>` | 整段引来的话：官方简介、官方字段、作者简介、补档声明 | 一眼分出「这是官方说法」与「这是我整理的」 | 把自己的说明塞进去，读者以为都是官方的 |
| `<ul>` `<ol>` | 并列项、步骤、文件清单、曲目表 | 一项一条，能扫 | 三五行的内容用列表反而占地方 |
| `<img>` | 封面 + 图本身是内容的图（样张、界面、曲目表） | 图能说的不用文字说 | 装饰图冲掉封面管线；外链图不生效 |
| `<strong>` `<em>` `<code>` `<del>` `<a>` | 行内强调：作品名、文件名、命令、失效率、外链 | 在段落里指出重点 | 一段里超过两处，等于没有重点 |
| 短代码 | 一键复制、警示卡、折叠、站内引用、官方按钮、编辑备注 | 见 `shortcodes.md` | 见 `shortcodes.md` |

允许的标签就这一份：

```
blockquote  hr  h3  h4  ul  ol  li  a  strong  em  code  del  img
```

`<p>` 不在名单里——分段交给空行。`<script>` `<style>` `<iframe>` `<table>`、内联 `style=`、`on*=` 不写。属性值用双引号，正文是片段，不加 `<html>` `<body>` 包裹。

## 怎么组合

**没有填空模板。** 选工具只看两件事：内容分几块、块之间是什么关系。

三个档位：**照抄** —— 封面第一张、段落间空行、短代码逐字、字段行全角冒号、`[internal]` 收尾，错一个就坏；**默认 + 逃生口** —— 字段块默认 `<blockquote>`（本地能验），要与存量同构就换 `[col_list]`，列表默认 `<ul>`；**自己定** —— 分几节、节名、段落顺序、图放几张、篇幅、要不要挂 alert。第三类没有正确解，照谁的帖抄都是错的，只能看手上有什么内容。

| 内容形态 | 自然用到的工具 | 说明 |
|---|---|---|
| 一部作品，字段多 | 封面 → `<hr />` → 分节 + 字段块 → 分节 + 段落 | 字段和叙述分开，读者各取所需 |
| 一部作品，字段少 | 封面 → 引来的官方简介 → `<hr />` → 一两段说明 | 字段不够撑一张表时，硬凑字段块更难看 |
| 多部作品并列 | 封面 → 一段总述 → `<hr />` → 引导句 + `<ul>` | 每项原样保留资源名 |
| 只有几段话（图贴、分流） | 封面 → 几段裸文本 | 一图一段，段后跟复制块 |
| 长到有多个主题 | 上面任一种 + `<h3>` 分节，需要时 `[collapse]` | 分节按内容真实的主题分 |

三种常见组合，当例子看，不是模板：

**字段型（单部作品，字段齐）**

```
<img src="file:///C:/…/images/9f2c1a4e77b0d3c8.jpg" alt="封面" />

<hr />

<h3>书籍信息</h3>

<blockquote>中文名称：城市猎人
别名：侠探寒羽良、City Hunter
出版社：东立出版社
册数：全35卷（平装）
原版名称：シティーハンター
原出版社：集英社（JUMP COMICS）</blockquote>

<h3>一些简介</h3>

剧情讲述了未来都市中，冴羽獠以私家侦探身份接活、并在灰色地带伸张正义的故事。国内引进版删去了大量情节。

<h3>归档说明</h3>

东立中文版扫图，300dpi，未裁边。

[internal]来源：东立官网书目（卷数、出版社、连载状态）／汉化组发布页（汉化组、版本标记）[/internal]
```

**目录型（多部作品并列）**

```
<img src="file:///C:/…/images/9f2c1a4e77b0d3c8.jpg" alt="封面" />

作者 2010 年起在同人展发布，画风偏肉感厚涂，2016 年后转商业连载。

<hr />

目录：

<ul>
<li>[社团 (作者)] 本子标题 [汉化组] [DL版].zip</li>
<li>[社团 (作者)] 另一本 [汉化组].zip</li>
</ul>

[internal]来源：社团发布页（作品清单）｜待人工确认：第 12 项缺汉化组标记[/internal]
```

**裸文本型（图贴、分流、字段很少的作品）**

```
<img src="file:///C:/…/images/9f2c1a4e77b0d3c8.jpg" alt="封面" />

作者自 2019 年起在 Fantia 发布套图，以制服题材为主。

共 57 组、1200 余张，PNG 原图，含无修正版本。

[internal]来源：https://www.patreon.com/…（张数、分辨率、发布日）｜待人工确认：实际文件数是否与发布页一致[/internal]
```

三种都有个共同点：**封面第一张，`[internal]` 最后一行**。这两条是硬的（封面管线、来源可复核），其余都可以按内容调。

### 小节名用站内的词

要分节时，站内惯用的名字是：`书籍信息`（159 篇）、`一些简介`（161 篇）、`归档说明`（41 篇）、`安装说明`、`目录`。用这些词，读者认得，同类帖也整齐。换成「基本信息」「作品简介」不算错，只是每换一次就少一点一致性——**同一个站长的帖里保持一致**比对齐某一个词更重要。

### 引语用 `目录：`

多部并列时，列表前那句引导语，站内 195 篇写的是 `目录：`。`同人本目录：` 与 `单行本目录：` 用于一个帖里有几类不同内容并排时，起区隔作用。

## 引用块装什么

`<blockquote>` 的含义是**「从别处整段引来的话」**——读者看到它，会默认这段不是本站写的。

| 装什么 | 场合 | 注意 |
|---|---|---|
| 官方剧情简介 | GALGAME、书籍、漫画 | 照抄，不改写，去掉促销话术 |
| 官方字段（名称、会社、平台、发售日…） | 游戏、漫画、音声 | 一行一条，全角冒号 |
| 作者 / 社团简介 | 合集帖开头 | 照抄，不掺评价 |
| 补档声明 | 补档、分流、旧帖重发 | 站内有一句流传很广的固定写法：`Tips：本贴是 2023 年的旧贴补档，不是新帖也没有更新，链接文件错误、无文件等请留言。` 年份按实际改，内容按实际情况调 |

自己的说明不放进引用块。要强调自己的话，用段落，或 `[alert]`。

## 字段块两种形式

字段多（≥5 项）时排成表比塞进句子好读。两种写法：

**`<blockquote>` + `字段：值`** —— 一行一条，单换行即 `<br />`。本地预览能看见实际效果，写错了立刻发现。

```
<blockquote>中文名称：城市猎人
出版社：东立出版社
册数：全35卷（平装）</blockquote>
```

**`[col_list]`** —— 站内原有的字段块，词一行、值一行交替，`dt_width` 控制词列宽度。存量的漫画帖里 161 篇用它。

```
[col_list dt_width="1"]
中文名称
城市猎人
出版社
东立出版社
[/col_list]
```

选哪个：`[col_list]` 与存量帖同构，但 `preview` 不解析短代码，词值行数错一个本地看不出来，要到站点才发现塌掉；`<blockquote>` 能在本地验。**同一个帖子用一种，同一个站长的帖尽量统一**——两类混着来，同类帖排版就不一样了。

字段行用全角冒号 `：`，一行一条。缺的整行删掉，不留空值。

## 篇幅

写到事实说完为止。存量帖的中位数是 628 字，四分之一在 400 字以内，四分之三在 1000 字以内——**这是手写时代的长度，不是目标**。agent 能把字段查得更全，比中位数长是正常的，前提是每一句都在给读者新增信息。

该写的：内容结构与玩法、卷数 / 曲目数 / 页数 / 时长、版本差异、安装与运行注意事项、语言与平台、系列内各作关系、文件形式。

不该为了凑长度做的：复述官方简介两遍、把字段拆成句子再写一遍、加「值得一玩」这类判断。

段落短，一段一到三句。

### 什么样的句子能用

同一个位置，两种写法的差别：

| 像文案（别写） | 可核对（写成） |
|---|---|
| 本作画面精美，剧情扣人心弦，是不可多得的佳作。 | 全篇 12 章单线剧情，通关约 20 小时，含全语音与 60 张 CG。 |
| 已完美汉化，附赠大量实用补丁。 | 已集成官方中文补丁与 v1.2.1 升级档；附修改器与存档编辑器，运行前加白名单。 |
| 合集收录了作者多年来的精选作品。 | 共 6 部，2019–2023 年发布，其中 2 部为无修正版。 |
| 解压后即可畅玩，非常方便。 | 解压后运行 `setup.exe`，安装路径不含中文；存档在 `%APPDATA%` 下，覆盖前先备份。 |

右栏只用了「来源里指得到的数字 + 具体的版本名」，没有形容词。读者从右栏能判断要不要下；左栏读完什么也不知道。

### 别写成 AI 腔

上一节管「写什么」，这一节管「长什么样」。写完扫一遍，命中就改——这十条是机器写的典型痕迹，读者一眼能认出。

| 痕迹 | 长这样 | 改成 |
|---|---|---|
| 三连排比 | 「更快、更稳、更省心」「画质、音效、剧情都在线」 | 留一个最能指到事实的，其余删 |
| 重要性膨胀 | 「堪称神作」「不可多得」「必玩」 | 删（红线 4 已划，这里是它在句子里的变体） |
| 系动词回避 | 「本作是一款由…打造的作品」「整体呈现出…的质感」 | 「X 开发，2023 年发行」 |
| 同义词轮换 | 一段里「作品 / 本作 / 该作 / 这部」轮着换 | 统一一个说法，或删掉主语 |
| 空洞加强词 | 「非常」「十分」「极其」「相当」「相当不错」 | 换成数字，或删 |
| 模糊归因 | 「玩家普遍认为」「业内评价很高」「被不少人称为」 | 给具体出处，或删 |
| 模板开篇 | 「在…的今天」「随着…的发展」「作为一款…」 | 直接从事实开始 |
| 全列表化 | 有连续逻辑的说明也拆成 bullet | 段落写叙述，列表只给并列项 |
| 加粗成瘾 | 一段三处 `<strong>` | 一段最多一处；重点靠句子结构，不靠加粗 |
| 收尾套话 | 「总之」「综上」「希望对你有帮助」 | 删。最后一句给事实或提醒 |

两类例外：**官方原文照抄**（`<blockquote>` 里的促销话术、商店页的形容词）不动，那是引用；**作品自带的名称**（副标题里的「完全版」「终极整合」）不动，那是专名。

自查的方式是扫，不是重写。看到一条改一条，改完不再通读——重写一遍容易改出新问题。

## 红线

四条，每条只在这里出现一次：

1. **下载信息归文件列表**。网盘链接、提取码、解压密码、种子页链接都不进正文。磁力是唯一例外——它没有别的承载形式，裹进 `[clip_board]`，一条一个。
2. **正文只描述作品本身**。「回复可见」「积分下载」「点这里」这类站内机制不属于正文内容。
3. **字段只取来源里能指到的值**。查不到就整行删掉：写「未知」「据推测」，或按印象补发售日、卷数、社团、CV，等于把不确定当事实发出去。
4. **判断句留给人**。评分、吐槽、玩梗、「神作」「必看」，这些不进正文。

## 六个词法

六个词法各有分工，串位是这份技能最容易犯的错。「真实在用词」是站内词表里的写法，挂词前用 `context` 复核一遍——表里没有的近义词挂上去就会变成新词。

| 词法 | 收什么 | 真实在用词 | 不收 |
|---|---|---|---|
| `resource_category` 分类 | 作品形态 / 站点栏目，**用 id** | 漫画、单行本、GALGAME、写真集、同人志、同人音声、番剧、图片集、游戏、COSPLAY | 题材、版本、作者 |
| `resource_original` 原作 | 所改编 / 衍生的 IP | 舰队Collection、东方Project、死或生、Fate、尼尔机械纪元 | 原创作品（写「原创人物」那类词或留空） |
| `resource_character` 角色 | 明确署名的角色 / 扮演者 | 原创人物、MIKU | 作者、社团 |
| `resource_author` 作者 | 社团 / 作者 / 绘师 / 演员（**不是发帖器里的账号作者**） | ωstar、Yuzu-Soft、ILLUSION、北条 司 | 原作 IP、出版社、整合者 |
| `resource_content` 内容描述 | 题材 / 情节 / 氛围标签 | 纯爱、奇幻、日常、校园、战斗、治愈、悬疑 | 载体形态、语言、版本 |
| `resource_other` 其他 | 形态 / 版本 / 地域 / 流派 | 合集、写真、完结、连载、硬盘版、3D动画、SFM、日韩、机翻、RenPy | 题材、角色 |

规则六条：

1. **每列 0–6 个，按相关度排序**。站内是按标签找资源的，一个错的标签比缺三个标签更麻烦。
2. **分类用 id**。它是唯一能带层级的词法（`context` 返回 `parent` 与 `path`），但当前实库是平铺的、全部 `parent=0`。用 id 的理由不是层级，是**接口按名称精确匹配，同名子分类会折叠到使用最多的那个**。
3. **其余词法优先用 `context` 里已有的词**（按使用次数降序，次数高的更可能是站内通用写法）。名字逐字照抄，不改大小写、不补空格、不换同义词。
4. **新词只在概念确实缺失时才造**，一条帖 1–2 个，只进 `resource_content`。名称直接写进 `terms`，推送时由站点创建；`preview` 回显成 `name:…`，看到就确认一下是不是真需要。
5. **载体进分类，形态进其他**。`写真` 既有「写真集」（分类）又有「写真」（其他），可以同时挂。
6. **作者列只放创作方**。发帖器里的「作者」是 WP 账号，由设置决定，`authorId` 一般不填。
