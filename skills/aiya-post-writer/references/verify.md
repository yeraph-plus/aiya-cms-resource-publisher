# 核实：来源分层、证据分级、冲突处理

`SKILL.md` 的工作流只说了「以官方源为准」。真跑起来会卡在三类判断上：这个页面算不算官方、两个来源打架听谁的、查到哪算够。这份文档给可执行的判据。

## 来源分层

| 层 | 是什么 | 能定什么 | 不能定什么 |
|---|---|---|---|
| **T1 官方** | 官网、商店页（Steam / DLsite / FANZA / BOOTH / Getchu / itch.io）、社团或作者主页、官方 SNS、出版社书目与自营店、官方新闻稿 | 任何字段，且是最高依据 | —— |
| **T2 权威二手** | VNDB、Bangumi、月幕 Galgame（ymgal.games）、摸鱼（moyu.moe）、Baka-Updates、批评空间、豆瓣读书、日文/英文维基 | 补 T1 没写的字段（别名、系列关系、中文译名、时长、原画与脚本） | 价格、发售日这类会被转载拖旧的值 |
| **T3 用户内容** | 贴吧、论坛、评测、UP 主视频、资源站转载页、网盘分享页 | 只能用来**发现线索**：原作名、别名、可能的系列、缺失字段的搜索方向 | 任何字段的唯一依据 |

一条规则：**字段先找 T1，T1 没有才用 T2 补，T3 只提供线索。** T3 里看到「这作有 8 个 DLC」，正确做法是去 T1 确认有没有、有几个，而不是直接写 8。

> 一个例外要知道：中文 Galgame 库里的三家常互相摘抄条目，同一处错会一起错。两个中文库一致、而日文 T2（VNDB / 批评空间）对不上时，按冲突处理（见下文），不按「多源一致」升级成 B。

## 网络：先走脚本，再谈降级

本机有一个常驻 HTTP 代理 `http://127.0.0.1:10808`。一部分站在直连下整段超时（DNS 通、TCP 不回应，几秒后被掐断）：itch.io、Steam 商店页、DLsite、GitHub、Bangumi（bgm.tv / api.bgm.tv）都属于这一类；百度、VNDB API 直连就正常。**所以「连不上」不等于「站点上没有这个字段」**，判 T1 不可达之前必须过代理。

取页面统一用脚本，它先直连、失败自动换代理，并把走了哪条线打出来：

```bash
node skills/aiya-post-writer/scripts/fetch-url.mjs "<url>" --out draft-page.html
# {"ok":true,"url":"…","via":"proxy","status":200,"out":"…","bytes":79510}
```

`via` 是 `direct` 还是 `proxy`，决定你在 `[internal]` 里怎么写这条来源。两条路线都失败时脚本退出 1，分行打印各自的原因——那才叫**真的不可达**，这时才换 T2 交叉或退到搜索索引，并在 `[internal]` 写明「直连与代理均不可达」。

三条注意：

- **不要为了省事全局挂代理**。百度、VNDB 这类直连更快，脚本按站点自动选；固定走代理只是让每条请求都绕一圈。
- **`stage --url` 不读代理**（`publisher.mjs` 是裸 `fetch`，没有 dispatcher）。取官方图先用这个脚本落盘，再 `stage <本地文件>`，见 `images.md`「操作」。
- 代理换端口设 `AIYA_PROXY` 环境变量，别去改脚本常量。两条路线都失败、且代理那条失败得极快（连 127.0.0.1 被拒），是代理没开，不是站点挂了。

## 怎么找到那几个站

上面那张表说的是「哪个站的什么字段可信」。这一节说的是「怎么落到那个站上」。载体该去哪些站、用什么词搜，在 `types/<载体>.md` 的「采信数据源」表里；这里只给适用的四条，顺序固定，命中即停。

1. **有唯一编号先搜编号。** `RJ0123456`、Steam AppID、ISBN 13 位、VNDB `v12345`。编号在搜索结果里几乎没有同名干扰页，一条查询直接落到作品页。
2. **没有编号，`原文名 + 站点名`。** `作品名 dlsite`、`作品名 vndb`、`作品名 steam`。原文名用日文原题或英文原名，别用中文译名——译名是转载站自己起的，官方页上不出现这个词。
3. **原文名也不确定，先定名再搜。** 拿中文名去 T2 数据库（VNDB / Bangumi / 月幕 / 摸鱼 / Baka-Updates / openBD）把原文名、作者或社团对出来，再回到第 2 条搜官方页。定名这一步只用数据库，不用资源站。
4. **结果被转载站淹掉，才加站点限定。** `site:dlsite.com 作品名`、`site:store.steampowered.com 作品名`。这是补救手段不是默认写法：站点换域、多语言子路径、地区版页面都会让 `site:` 漏掉真页面，漏了也不会有任何提示。

查询框里放关键词，不放问题。`这个社团还出过什么` 这类问句得到的是一个读起来很像真的答案；`社团名 dlsite` 得到的是商店页。

搜索结果里的标题不等于页面内容。点进去先对三件事：作品名对得上（原文名或译名之一）、这是**作品页**而不是搜索页/标签页/列表页、页面上有能跟结果对上的唯一键（RJ 号 / AppID / ISBN / VNDB id）。三条有一条对不上，退回结果页换一条查，别在那一页上凑合读。

白名单没命中不等于可以退到转载站。T3 只提供线索：拿它的说法回 T1 复核，复核不到就留空。这跟「查不到就留空」是同一条规则的两种现场。

## 证据等级

每个要写进正文的字段，落笔前心里有个等级：

| 等级 | 判据 | 去处 |
|---|---|---|
| **A 官方确认** | T1 页面明确写着，且能指到具体页面 | 正文，`[internal]` 记来源页 |
| **B 多源一致** | 两个独立 T2 一致，或 T1 暗示 + T2 确认 | 正文，`[internal]` 记两处 |
| **C 单一来源** | 只有一个出处，且不是 T1 | 正文写「据 <来源名>」，或不写 |
| **D 线索** | 只在 T3 出现，或指不到具体页面 | 不进正文，只进 `[internal]` 的待确认 |

## 冲突怎么处理

两个来源给出不同数字（发售日、卷数、时长、CV），按这个顺序判：

1. **是不是不同版本** —— 多数冲突是这个：实体版 / 数字版、初版 / 完全版 / 廉价版、日版 / 中文版、体验版 / 完整版。先确认比的是不是同一个东西。
2. **谁更新** —— 官方页会改，转载页往往停在旧值。看官方页有没有更新公告。
3. **仍然打架** —— 正文不写定论：写「官网标 25 小时，DLsite 标 20 小时」，或者只写没争议的部分。`[internal]` 记下冲突与两个链接。

**两条都留下。** 抹平冲突是这类内容最常见的失真，而且读者事后一定能发现。

## 查到什么程度停

够了的判据：正文要写的每个数字、六个词法的每一列，都有 A 或 B。

该停下来问人的三种情况：

- 来源域与结构指纹指向两个不同载体（见 `dispatch.md` 冲突一节）。
- 关键字段（名称、卷数、发售日）只有 T3。
- 输入是一个压缩包，但没有任何页面可查——先问用户这是哪部作品。

**查不到就留空**，并在 `[internal]` 写「未查到：CV 名单、DLC 数量」。正文写的是来源里指得到的值；「据推测」「约」「大约」这类说法和 T3 的模糊传闻，位置都在 `[internal]` 的待确认里。

## 顺带记风险信号

核实过程会顺带看到一些决定「要不要挂 `[alert]`」的信号，看到了就记下来，别等写正文时凭印象：

| 看到什么 | 意味着 |
|---|---|
| 包里有 `.exe` / `.bat` / `.cmd`，来源不是官方 | 二次打包，完整性未知 |
| 需要管理员权限、写系统目录、改注册表、装驱动 | 运行有代价 |
| 汉化补丁、破解补丁、修改器、单文件启动器 | 会被杀软拦截 |
| 文件名带「整合」「免安装」「绿色版」且非官方发布 | 整合方改了内容 |
| 来源站多次跳转、网赚中转、要求关注才能看 | 来源可靠性低 |
| 官方页已下架、社团停止活动 | 只能靠转载，标明 |

`[alert]` 的 `type` 取值与写法见 `shortcodes.md`。

## 记录格式

一段 `[internal]` 里把上面四件事一次记完：

```
[internal]来源：
T1 store.steampowered.com/app/1234560（八字段全部）
T1 官方推特 2024-03-11（发售日由 03-08 更正为 03-15）
T2 VNDB v12345（系列关系、原作）
冲突：DLsite 标时长 20h，官网标 25h（疑为体验版/完整版差异）
未查到：CV 名单、DLC 数量
风险：包内 setup.exe 为二次打包，非官方发布
待人工确认：实际文件是否含全部 DLC[/internal]
```

没有的那几行就整行不写。别为了对称凑满四类。
