# 兜底：归不了类的

## 什么时候用它

- 三个信号都指不到一个载体：来源域不认识、结构指纹中性、词法落不上。
- 站内有分类但没有专用组合的形态：番剧 / 里番 / 电影 / 剧场版 / 音乐集 / 播客 / 主机 ROM。
- 一批混合内容，逐条都归不了。

归不了类**不是失败**。硬套一个载体写出来的帖子，结构是错的，人还得整篇重写；通用整理的帖子至少事实是对的。

## 采信数据源

搜索词怎么构造（编号优先、原文名 + 站点名、落页三条判据）见 `references/verify.md`「怎么找到那几个站」。这个载体没有专属站点，按子形态挑行，命中即停。

| 子形态 | 搜索词 | 落在哪 | 能定什么 |
|---|---|---|---|
| 番剧 / 里番 / 电影 / 剧场版 | `原文名 公式サイト` → `原文名 bangumi` → `原文名 anilist` | 官方站 → Bangumi → AniList | 话数、放送日、制作、CV、原作 |
| 音乐集 / 演唱会 | `专辑名 discogs` 或 `专辑名 vgmdb` | Discogs / VGMdb / 厂牌页 | 曲目数、碟数、发行日、艺人、品番 |
| 主机 ROM + 模拟器 | `游戏名 公式` → `游戏名 gamefaqs` | 官方站 → GameFAQs | 发售日、平台、版本、语言 |
| 其它 | `原文名 公式` → 退到百科 | 官方发布页 → 百科 | 名称、作者、发布日、版本 |

采信边界：

- 百科只能补「别名 / 发布日期 / 制作人员」，定不了版本与语言支持。
- 资源站、搬运页、字幕组发布页只当线索；这类帖最容易在「几个语言音轨」「含不含特典」上写错。
- 子形态本身判不准时，把「查到了什么、卡在哪」写进回报，别用推测把表格填满。

## 标题

载体词逐字取自 `resource_category` 词表（先 `context --taxonomy resource_category` 看一眼）。词表里没有这个类型词就不写载体前缀，只留形态词（`合集` `搬运` `完结`），写成 `[合集] 名称`——`[其他]` `[杂项]` 这类自造前缀站内认不出来。

## 正文

没有固定形状，按手上有的信息挑工具。一个可用的组合：

```
<img src="file:///…" alt="封面" />

一句话说明这是什么：类型、来源、规模。

<blockquote>语料中的官方信息，照抄。</blockquote>

其余事实性说明：名称、作者、版本、语言、载体。缺失的留空，不推测。

[alert type="error" name="来源未验证"]本包来自二次转载，未与官方发布比对，完整性未知。[/alert]

[internal]来源：…（用了哪些页面、各贡献了什么字段）｜待人工确认：…[/internal]
```

内容撑不起来的分节比没有分节更难看，所以 `<h3>` 与 `<ul>` 只在确实有两三个并列小节时才出现。这类帖最容易碰到来源不明、来源站有风险、需要手动改系统的包：判定是真的就用 `[alert]` 明说，别写在段落里糊过去（规则见 `references/shortcodes.md`）。

## 分类

| 词法 | 填什么 |
|---|---|
| `resource_category` | 归类没把握就**留空数组**，不硬猜。有把握就挂最泛的那个 |
| `resource_other` | 站内有对应词就挂（番剧、里番、搬运…） |
| `resource_author` | 有明确创作方就填 |
| `resource_content` | 题材 0–6 个 |
| `resource_original` / `resource_character` | 改编或角色明确时才填 |

分类留空的帖子在发帖器里显示为无分类，人能一眼看出「这条要手工归类」——这正是想要的效果。

## 回报时说清楚

这类帖子的回报必须多一句：`分类未定，正文为通用整理（依据：…）`。人看到这句才知道要人工接手，而不是以为 agent 都处理好了。
